# 174 — Codification gate

## 1. Problem

OAP's security and correctness findings are generated
by several substrates:

- **`crates/axiomregent`** — semantic search,
  checkpoint inspection, GitHub integration. Produces
  findings about code state and history.
- **`crates/provenance-validator`** — per spec 121,
  validates claim provenance across artifacts.
  Produces findings about broken provenance chains.
- **`crates/policy-kernel`** — the governance control
  plane. Produces findings about policy violations.

Today, when one of these substrates generates a
CRITICAL or HIGH finding (a real security issue, a
real correctness regression), the agent typically:

1. Reads the finding.
2. Decides on a fix.
3. Implements the fix.
4. Closes the conversation.

What's missing: the *codification step*. The finding's
class is not recorded as institutional memory anywhere
the next agent on the next project can find it. The
next agent — facing a similar setup — has to rediscover
the same lesson.

AIDE-VELOCITY-HARNESS's `check-finding-codified.mjs`
gate closes this loop. The intent doc §8.7 names the
OAP analogue:

> *"Codification gate analogue. Per the harness's
> `check-finding-codified.mjs` pattern. For every
> CRITICAL/HIGH finding generated by `axiomregent` /
> `provenance-validator` / `policy-kernel`, require a
> spec-spine entry before the conversation closes."*

The convergence doc §2.I amplifies:

> *"Codification gate analogue. For every security or
> correctness finding generated by `axiomregent` /
> `provenance-validator` / `policy-kernel`, require a
> spec spine entry under `standards/security/` (or
> under the implicated spec's `§Constraints`) **before
> the conversation closes.** This is the
> `check-security-finding-in-spec.mjs` equivalent —
> institutional memory at the harness level,
> mechanically enforced."*

## 2. Decision

Add a `codification-gate` binary that fires as a Stop
hook entry on the spec 166 chain. The binary:

1. Reads finding artifacts emitted by `axiomregent`,
   `provenance-validator`, and `policy-kernel` during
   the session.
2. Filters to CRITICAL / HIGH severity.
3. For each filtered finding, checks whether the
   finding's class is represented in the spec spine.
4. Blocks session closure if any unrepresented
   CRITICAL or HIGH finding exists.

### 2.1 Where findings codify

The gate accepts two representations:

- **Dedicated security spec.** A spec under
  `standards/security/NNN-<finding-class>/spec.md`
  declaring the class and the response/mitigation.
  This is the canonical home for cross-cutting
  security lessons.
- **`§Constraints` section on the implicated spec.**
  When the finding is specific to one spec's
  surface (e.g., a finding against the tool registry
  surface lives under spec 067's `§Constraints`),
  the constraint section is the right home. The
  spec's frontmatter gains a `constrains:` edge per
  spec 130's relationship graph.

The gate is agnostic to which home the codification
takes; it requires representation *somewhere* in the
spec spine.

### 2.2 Class matching

Like the harness's gate, class matching is heuristic:
the finding's ID, title keywords, or category tags
are matched against spec text. The intent doc
acknowledges this is gameable:

> *"The codification check uses keyword matching
> (first 3 significant words of a finding title, or
> the finding ID) against the standards file. This is
> heuristic — a sufficiently paraphrased finding title
> could pass without genuine codification. The check
> is honest about this (no formal semantic matching);
> it relies on the AI agent to write meaningful rule
> text."*

Spec 174 adopts the same honest-heuristic posture.
Improvements (semantic matching via embeddings;
LLM-checked equivalence) are future refinements.

### 2.3 Override semantics

Like the spec 166 chain, the gate supports operator
override. The operator can mark a finding as
intentionally-not-codified (e.g., a transient finding
that doesn't represent a generalisable class) by
writing a `.codification-override.yaml` entry with a
reason. The override is logged to the governance
certificate chain so the audit trail includes the
operator's reasoning.

### 2.4 Composition with the gate chain

Spec 174's gate runs as an entry on the spec 166 Stop
hook chain. It joins `codebase-indexer check`,
`spec-lint`, and `spec-code-coupling-check` as a
fourth Stop entry. The chain semantics (block on
non-zero exit, structured diagnostic surfacing,
operator override) inherit from spec 166.

## 3. Functional Requirements

- **FR-001** A `codification-gate` binary lives under
  `tools/oap/codification-gate/` and is invoked as a
  Stop hook entry per spec 166's chain semantics.
- **FR-002** The binary reads finding artifacts from
  the session's working state: `axiomregent` output,
  `provenance-validator` reports, and `policy-kernel`
  policy-violation records.
- **FR-003** The binary filters to CRITICAL and HIGH
  severity findings; LOW and MEDIUM findings do not
  trigger the gate.
- **FR-004** For each filtered finding, the binary
  searches the spec spine for representation:
  - A dedicated spec under `standards/security/` (or
    a similar designated location) whose body
    mentions the finding's class.
  - A `§Constraints` section on the implicated spec
    whose body mentions the finding's class.
- **FR-005** Class matching is heuristic: the
  finding's ID, title keywords, and category tags
  are matched against spec text. The matching is
  conservative (false positives are preferable to
  false negatives — a finding falsely deemed
  codified is a failure mode the spec acknowledges).
- **FR-006** If any CRITICAL or HIGH finding has no
  representation, the binary exits non-zero with a
  diagnostic naming the finding(s) and the locations
  the gate searched.
- **FR-007** An operator can override per-finding via
  a `.codification-override.yaml` entry with a
  reason. Overrides are logged to the governance
  certificate chain.
- **FR-008** The gate runs in addition to (not in
  place of) the existing spec 166 chain entries.
  All entries must pass; failures compose.
- **FR-009** The gate respects spec 103's
  governed-artifact-reads discipline. Finding
  artifacts are read through their typed consumer
  surfaces (`axiomregent` etc), not via ad-hoc
  parsing.

## 4. Success Criteria

- **SC-001** A session in which `axiomregent` raises
  a CRITICAL finding cannot close until the finding
  is codified in the spec spine.
- **SC-002** Codifying a finding (writing the rule
  into `standards/security/NNN-*/spec.md` or
  into the implicated spec's `§Constraints`) causes
  the next gate run to pass without operator
  override.
- **SC-003** A session producing only LOW or MEDIUM
  findings passes the gate without codification
  requirements.
- **SC-004** An operator override for a transient
  finding logs to the certificate chain with the
  operator's reasoning.
- **SC-005** A future session on a different project
  inherits the codified rule via the spec spine —
  the rule is read by agents inheriting the kernel
  per spec 167.

## 5. Scope

### In scope

- The `codification-gate` binary.
- The class-matching heuristic.
- The Stop-hook integration.
- The operator override surface.
- The audit-emission integration with the
  governance certificate.

### Out of scope (deferred)

- **Semantic matching via embeddings.** First cut
  uses keyword heuristics. Embeddings-based class
  matching is a future refinement.
- **Cross-project finding aggregation.** Spec 174
  is per-session. A future portfolio concern may
  aggregate findings across projects.
- **Auto-codification.** The gate enforces
  codification; it does not generate the spec
  text. A future helper may propose draft
  codifications via LLM synthesis but spec 174
  does not include it.
- **Codification of historical findings.** The
  gate fires forward — findings raised after spec
  174 lands. Backfilling pre-174 findings is an
  operational catch-up, not part of the spec.

## 6. The harness analogue posture

The harness's gate (CLAUDE.md hook chain item 6)
treats `02-security.md` as living institutional
memory. Spec 174 treats the spec spine the same way:
the spine is *not* a static design record — it is
the substrate's accumulating doctrine. Every
codified rule expands the corpus; every future agent
reading the kernel inherits the corpus.

The intent doc §4.4 already names this comparison:

> *"Convention-derived from `./velocity/v?/output/*.md`
> [in AIDE] / Spec-spine (authored markdown →
> compiler-emitted JSON) — drift-impossible by
> construction [in OAP]"*

Spec 174 makes the spine actively grow in response
to discovered risks, not just statically express
intent.

## 7. Compliance

Spec 174 strengthens **ASI04 (Agentic Supply Chain)**
by ensuring discovered provenance failures translate
into spine entries that future projects inherit. It
also strengthens **ASI06 (Memory & Context
Poisoning)**: a poisoned source detected once and
codified is structurally impossible to silently
encounter again — the spine carries the lesson.
